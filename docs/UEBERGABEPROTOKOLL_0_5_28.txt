ARCHITEKTUR DER KORREKTUR
- Der EINZIGE Python-Worker tools/ember_py_worker.py wird von Native
  und Compose mit identischem Code genutzt.
- Jeder Worker-Job startet im BISHERIGEN isolierten Docker-Container
  zuerst ein vertrauenswuerdiges Python-Preflight-Bootstrap.
- Das Bootstrap prueft den vollstaendigen Script-Quelltext mit
  Python compile() ohne ihn auszufuehren.
- Syntaktisch gueltiger Code startet sofort mit os.execv die bisherige
  Python-CLI (python -I /work/main.py), ohne neuen Modellaufruf.
- Bei SyntaxError/IndentationError/TabError wird mit einem speziellen
  Exitcode und einer begrenzten Metadatennachricht abgebrochen.
- Kein ungueltiger Python-Code erreicht die eigentliche Ausfuehrung.
  Das gilt ebenfalls bei Modellen, die [PY] und Python-Fences erzeugen.
- Bei modellgeneriertem Code wird hoechstens EIN zusätzlicher serieller
  Korrekturaufruf angefordert; er enthaelt Originalauftrag, originalen
  Script-Text und die sichere Fehlermetadatenposition.
- Nur Ausgangsskripte bis 24000 Bytes werden automatisch korrigiert.
  Groessere bleiben unveraendert gestoppt.
- Zweiter Syntaxfehler: Abbruch statt weiterer Modellanfragen.
- Nach einer Syntaxkorrektur werden bestehende Datei-Reparaturaufrufe
  nicht nochmal angeschlossen (kein mehrfaches Modell-Looping).
- Backendgenerierte HTML/ZIP-Writer duerfen nicht vom LLM ersetzt werden.

SICHERHEIT
- Compiler im eingeschraenkten Sandbox-Container, niemals auf dem
  produktiven Host ausserhalb der Sandbox.
- Unveraenderte Isolation (Ressourcen, Docker-Netz, Laufzeitlimits).
- Kein raw Python-Code oder stderr in nutzerseitigen Work-Events.
- Nur Fehlertyp und Zeilennummer sind im oeffentlichen Protokoll erlaubt.
- Fehlerfreie Syntax ist keine Garantie fuer Laufzeit- oder Logikfehler.
