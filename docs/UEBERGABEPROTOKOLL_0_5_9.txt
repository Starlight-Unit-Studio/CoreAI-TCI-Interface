2. AGENTENLAUF UND ABBRUCH
Migration 013: stu_console_agent_runs mit eindeutiger Run-ID pro Benutzer,
Sitzung, Turn und Aktion. Zustaende atomar; SSE-Reconnect wiederholt
keine unbestaetigten Modellaufrufe. Antworten werden nur an einen
tatsaechlichen eigenen Turn gebunden.

Abbruch: api/console_actions.php akzeptiert POST cancel_run mit CSRF,
Sitzung und eigener Run-ID. Wartende Runs werden direkt cancelled;
laufende und Browser-Runs erhalten cancel_requested_at. Der Server
prueft das Flag an Modell-/Werkzeuggrenzen und in cURL-Fortschritt.
Der Transportabbruch beweist NICHT, dass ein Cloudprovider intern
sofort die Arbeit beendet. Keine automatische Wiederholung.

Die Chatoberflaeche zeigt beim laufenden Run eine Stop-Schaltflaeche
und kann dessen sicheren Status per GET run_status abfragen.
Die Timeline bleibt unveraendert kontogebunden; keine rohen Gedanken,
Prompts, Werkzeugsourcen oder geheimen Fehlerausgaben werden geteilt.

Browser-Delegation bindet browse_job_id an den eigenen Agentenlauf.
Nach Jobabschluss werden echte gespeicherte Antworten mit dem Run
verknuepft oder der Run mit failed/interrupted/cancelled markiert.
Keine automatische Wiederaufnahme eines unklar beendeten Cloudaufrufs.
Eine allgemeine mehrstufige Werkzeug-Checkpoint-Fortsetzung ist P07/P26.

3. GLOBALE SERIELLE MODELLWARTESCHLANGE
Migration 013: stu_console_model_queue mit monotoner queue_id,
FIFO-Ticket, optionalem Agentenlauf, Eigentuemerverbindung,
Zeitstempeln und Endstatus. Jeder Ollama-HTTP-Modellaufruf nutzt
diese Warteschlange und denselben MariaDB GET_LOCK.
Warte-Tickets werden per Heartbeat erneuert, abgestorbene Wartende
werden markiert. Eine GET_LOCK-Verbindung bleibt die einzige
autoritative Modellspur, auch fuer gpt-oss:120b via Ollama Cloud,
Reflect, Warmup, SSE und synchrone Folgeaufrufe.
Verschachtelte Aufrufe im selben PHP-Worker sind referenzgezaehlt.
Terminale Tickets werden nach sieben Tagen begrenzt bereinigt.

Wartezeit derzeit auf 90 Sekunden begrenzt; bei voller Warteschlange
kann der Aufruf scheitern. Noch KEIN unabhaengiger Hintergrund-Scheduler.
Ein abgestuerzter PHP-Prozess verliert seine DB-Sperre; der Zustand
einer bereits gestarteten Remote-Cloudanfrage kann dabei unbekannt
bleiben. Solche Agentenlaeufe werden nicht automatisch erneut gestartet.
